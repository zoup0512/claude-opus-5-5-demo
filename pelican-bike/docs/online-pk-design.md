# 鹈鹕骑单车 · 双人在线 PK 版 — 设计文档

> 版本 v1.0 · 2026-10-03
> 基于现有单机版（esbuild + Three.js，~5200 行源码）改造，部署目标为飞牛 NAS（192.168.110.140）。

---

## 0. 概述

把现有的单机海岸骑行改造成**两名玩家在同一片程序化海岸线上实时对战的夺鱼竞赛**：

- 双方各自操控自己的鹈鹕骑行，能实时看到对方的 3D 形象；
- 服务器下发**完全相同的刷鱼波次**（类似俄罗斯方块对战的双人同序列），拼手速和路线选择；
- 金鱼除了 5 分，还会掉落**干扰技能**（逆风、海鸥偷鱼、迷雾、尾流加速），形成攻防；
- 限时 3 分钟，分数高者胜，支持再来一局。

**非目标（本期不做）**：3 人以上房间、观战、排位/账号体系、公网联机（预留路径）、移动端适配优化（沿用现有触屏按钮）。

## 1. 玩法设计

### 1.1 对局流程

```
进入页面 → 输入昵称 → 【单人骑行】（保留原版）/【创建房间】/【加入房间】/【快速匹配】
   ↓
房间等待页（展示房号 4 位字母，如 QF3K；可复制 ?room=QF3K 链接直接邀请）
   ↓ 双方就绪，房主点开始
服务器 3-2-1 倒计时（对局时间锁定为黄昏 17:30，画面最好看且无玩法影响）
   ↓
对局 3 分钟（默认，房主可选 2/3/5）
   ↓
结算页：领奖台 + 双方数据（得分/鱼数/金鱼数/最高速度/里程）→ 再来一局 / 回大厅
```

### 1.2 计分规则

| 行为 | 分数 | 说明 |
|---|---|---|
| 普通鱼 | +1 | 与原版一致 |
| 金色鱼 | +5 | 出现概率约 12%（服务器决定），沿用原版 |
| 特技（T 放手展翅） | +1 | 落地成功才计分，每波上限 1 次，防止刷分 |
| 终场里程领先者 | +3 | 鼓励不龟速 |

**平局处理**：进入 30 秒加时「金鱼决胜」——先吃到金鱼者胜，30 秒无人吃到则按里程判定。

### 1.3 刷鱼波次（公平核心）

- 服务器每 **8 秒 ±1 秒**（服务器 RNG）广播一个波次：`{waveId, pattern}`，pattern 决定 5 条鱼的横向分布（连续 z 值）、跃出节奏、哪条是金鱼。
- 两个客户端收到后**在各自玩家前方**渲染同样的波次——序列相同、相对位置相同，比的是操作。
- 漏掉的鱼 4 秒后沉回海里，波次作废。
- 对局内的昼夜、海浪种子由服务器统一下发；海浪振幅调小（减少网络同步下的视觉抖动干扰）。

### 1.4 干扰技能（PK 味道）

吃到金鱼的一方，除了 +5 分，获得一个随机技能（按 **G** 释放，手机端出现技能按钮）：

| 技能 | 效果 | 时长 |
|---|---|---|
| 逆风 🌬️ | 对手速度上限 -30% | 3s |
| 海鸥 ⬅️ | 从对手得分偷 2 分（不低于 0） | 即时 |
| 迷雾 🌫️ | 对手画面边缘起雾 | 2.5s |
| 尾流 💨 | 自己加速 +25% | 3s |

技能效果由服务器下发并广播，客户端只做表现（音效、粒子、HUD 提示）。同一时间每人最多持有 1 个技能，重复获得则覆盖。

### 1.5 互动彩蛋（零成本社交）

沿用现有按键，对局中天然成为互动：**B 车铃**、**H 鹈鹕大叫** 会以事件消息传给对手并播放（音量按距离衰减）。对手骑在你的镜头里时，能听到他的铃铛声。

## 2. 总体架构

```
┌──────────────┐  WebSocket (JSON, 20Hz)  ┌──────────────────┐
│  客户端 A     │◄────────────────────────►│                  │
│ (浏览器)      │   /ws (经 8091 反代)      │  Node.js 游戏服务器│
├──────────────┤                          │  (NAS 容器:8092)  │
│ Three.js 场景 │                          │  ├ 房间管理        │
│ 本地物理/IK   │                          │  ├ 波次调度(RNG)   │
│ 远端鹈鹕插值  │                          │  ├ 计分/技能权威   │
└──────────────┘                          │  └ 断线重连        │
        ┌──────────────┐                  └──────────────────┘
        │  客户端 B     │◄───────────────────────┘
        └──────────────┘
   静态资源仍由现有 nginx:alpine 容器(8091)提供，并新增 /ws 反向代理
```

### 2.1 权威划分（务实取舍）

| 内容 | 权威方 | 理由 |
|---|---|---|
| 玩家自身移动/物理/跳跃/特技 | 客户端 | 避免把单车物理移植到服务端；本作非对抗碰撞型格斗，手感优先 |
| 刷鱼序列、金鱼归属 | 服务器 | 公平性核心 |
| 捕鱼判定 | 客户端上报，服务器校验 | 客户端检测碰撞（沿用 fish 逻辑），上报 `catch{waveId,fishId}`，服务器在自己维护的波次池里核销 |
| 分数、技能、倒计时、胜负 | 服务器 | 防篡改底线 |
| 移动作弊 | 服务器钳制 | 收到的 speed 超过物理上限 ×1.15 视为非法，钳制并记录 |

> 这是「休闲 2 人局」的合理反作弊深度：改包发包最多多核销当波次池里的鱼（池是有限的），速度作弊会被钳制。不追求电竞级。

### 2.2 为什么不用 WebRTC P2P

2 人局 P2P 延迟更低，但需要 STUN/TURN、房主即主机导致权威不对称、断线即全挂。NAS 局域网内 WebSocket 往返 <5ms，公网部署时集中式服务器也只需一条端口。**选择集中式服务器**。

## 3. 通信协议

传输：WebSocket，JSON 文本帧（2 人局带宽无压力，约 5KB/s/人；后续可换二进制不动结构）。

### 3.1 消息一览

**客户端 → 服务器**

| type | 载荷 | 说明 |
|---|---|---|
| `hello` | `{name}` | 连接后首包，昵称（≤12 字符，过滤敏感词） |
| `create` | `{duration}` | 创建房间，返回房号 |
| `join` | `{code}` | 加入房间 |
| `quick` | `{}` | 快速匹配（排队第 2 人即成局） |
| `ready` / `unready` | `{}` | 等待页准备 |
| `start` | `{}` | 房主开始 |
| `state` | `{d,l,v,y,j,tk}` | 20Hz 自报状态：里程 d、横向 z=l、速度 v、跳跃相位 y、特技标志 tk |
| `catch` | `{wave,fish}` | 捕鱼上报 |
| `skill` | `{}` | 释放技能 |
| `emote` | `{k}` | bell / squawk |
| `ping` | `{t}` | 时钟同步 |
| `again` / `leave` | `{}` | 再来一局 / 离开 |

**服务器 → 客户端**

| type | 载荷 | 说明 |
|---|---|---|
| `welcome` | `{id,proto}` | 分配玩家 id |
| `room` | `{code,players,host,duration,state}` | 房间全量状态（等待/倒计时/进行中/结算） |
| `countdown` | `{endAt}` | 服务器时间戳，客户端按偏移渲染 3-2-1 |
| `match` | `{seed,hour,endAt}` | 开局：世界种子、锁定时刻、截止时间 |
| `wave` | `{id,pattern}` | 刷鱼波次 |
| `caught` | `{who,wave,fish,value}` | 广播核销结果与得分 |
| `opp` | `{...state}` | 转发对手 state（原样 relay） |
| `skillFx` | `{by,kind,target}` | 技能生效 |
| `emote` | `{by,k}` | 铃/叫 |
| `score` | `{a,b}` | 分数快照（每次变化推送） |
| `end` | `{result,stats}` | 终局：胜负 + 双方数据 |
| `pong` / `error` / `kick` | | 常规 |

### 3.2 同步与插值

- `state` 上报 **20Hz**（50ms），服务器 relay 即转发；对手客户端缓冲 **100ms** 做插值（位置、朝向、踏频相位），跳跃/特技用事件触发本地动画而非插值。
- 远端鹈鹕的车轮转速、踏频 IK 全部由速度推算（`v → cadence → IK`），无需同步骨骼——这是原版程序化动画的红利。
- 时钟同步：连接时 `ping/pong` 3 次取最小 RTT/2 偏移，倒计时与终场以 `endAt` 服务器时间判定。

### 3.3 断线重连

- 断线后服务器保留座位 **15 秒**，重连携带 `?room=CODE&resume=TOKEN` 自动回归，分数保留、位置以上次快照恢复，重发当前波次。
- 超时未归 → 判负，对手胜利结算。终局前 10 秒断线同样适用。

按现有模块（不做大重构，`S` 单例保留为「本机玩家」语义）：

| 文件 | 改动 | 规模 |

| `src/audio.js` | 远端事件音：对手铃/叫/捕鱼（音量按距离衰减）、技能音效、倒计时/胜利音 | +~80 行 |

| `index.template.html` | 大厅覆盖层（昵称/房间/匹配）、PK 顶栏、结算弹窗、技能按钮、分享链接 | +~150 行 CSS/HTML |
| `build.mjs` | 不变（仍单文件打包）；输出加 `?v=` 版本查询参数防缓存 | ~3 行 |

## 5. 服务端设计

**技术栈**：Node.js 22 + `ws`，零数据库（房间全内存，重启即清空——休闲局可接受；后续想存战绩再加 SQLite）。

```
server/
  index.js      # HTTP /healthz + WS 升级，端口 8092
  room.js       # 房间生命周期：waiting → countdown → playing → ended → (again)
  match.js      # 波次调度（seeded RNG）、计分、技能、终局判定、重连快照
  protocol.js   # 与客户端共享的消息定义（构建时复制进 src/net/）
```

**房间状态机**：

```
waiting ──双方ready+房主start──► countdown(3s) ──► playing ──endAt到期──► ended
   ▲                                                              │
   └────────────────────── both again ◄──────────────────────────┘
  任意时刻 leave → 若对局中，对方直接胜
```

**校验规则**（`match.js`）：
- `catch`：wave 必须存在且未过期，fish 未被该玩家核销过，单鱼全局一次（两人抢同一条鱼时先到先得，另一端收到「落空」反馈音）；
- `state.v` 超过档位物理上限 ×1.15 → 钳制并计数，10 次踢出房间；
- 消息速率上限 40 条/秒/连接，超限断开；
- 单帧载荷上限 4KB。

## 6. 部署方案（NAS 实施细节）

```
192.168.110.140
├── pelican-bike            (现有) nginx:alpine :8091  静态站点
│     └── 新增挂载 nginx.conf：location /ws → proxy_pass http://127.0.0.1:8092
│            （WebSocket upgrade 头 + 60s read timeout）
└── pelican-bike-server     (新增) node:22-alpine :8092（仅绑定 127.0.0.1，由 nginx 反代）
      └── docker run -d --name pelican-bike-server --restart unless-stopped \
            -v /vol1/docker/pelican-bike-server:/srv -w /srv node:22-alpine \
            node index.js
```

- 客户端永远连 `ws://<host>/ws`（同源，未来换域名/HTTPS 零改动）。
- 升级流程：本地 `node build.mjs` → SFTP 推 `dist/index.html` 到 `/vol1/docker/pelican-bike/` → 推 `server/` 并 `docker restart pelican-bike-server`。写一个 `deploy.sh` 一键完成。
- **公网联机（后续）**：NAS 上已有 frps 容器，映射 8091 即可；或走 fnOS 自带反代 + Let's Encrypt。协议不用变。

## 7. 性能与容量

- 单客户端带宽：state 20Hz × ~120B ≈ 2.5KB/s ↑，下行（opp + wave + score）≈ 3KB/s。两人民用网络绰绰有余。
- 服务器单房间内存 < 64KB；NAS 16GB 内存跑 500+ 房间无压力，实际瓶颈是没人陪玩 😄。
- 渲染端：多渲染一只鹈鹕 + 一辆车（约 1.5 万三角），原场景 60fps 基础上预计掉帧 <5%。

## 10. 风险与开放问题

| 风险 | 应对 |
|---|---|
| `S` 全局单例深植于 main.js（1399 行），PK 分支容易牵一发动全身 | 不重构，PK 状态独立成 `P` 对象，只在渲染/输入处汇合；单人模式回归测试每阶段必跑 |
| 捕鱼判定在客户端，理论可发包刷分 | 核销池 + 速率钳制，接受休闲级安全性；上强度再迁判定到服务端（需上传统一世界坐标） |
| 镜像波次下双方里程差距大，节奏感受不同 | 波次按**时间**而非里程触发，双方收到即刷在自己前方，天然无追赶问题 |
| 公网联机时的 UDP 不可用/端口受限 | 已选 WS 单端口走 frp/反代，无此问题 |
| 开放问题 | ① 技能是否过于干扰（可做成默认关闭的「友谊赛」开关）② 是否需要简单战绩页（SQLite）——建议 v2 再说 |
